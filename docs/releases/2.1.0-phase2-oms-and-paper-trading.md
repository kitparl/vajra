# Phase 2 slice 2: order management, paper venue and order API

## Summary
`brahma` (core-service) now accepts orders over REST, runs them through an order state machine with idempotent placement, fills them on a paper venue against live Delta testnet quotes, and keeps fills, positions, realized/unrealized PnL and fees, with every change audited. Second slice of Phase 2 (enhancement → minor).

## Changes
- **Order state machine:** 12 states (`NEW, RISK_REJECTED, APPROVED, SENT, ACKED, PARTIALLY_FILLED, FILLED, REJECTED, UNKNOWN, CANCEL_REQUESTED, CANCELLED, EXPIRED`); every allowed and forbidden transition is tested. A venue error moves an order to `UNKNOWN`; it is never re-sent.
- **Idempotency:** `Idempotency-Key` header required (1–64 chars `[A-Za-z0-9_-]`). `client_order_id = "v" + 31 hex chars of SHA-256(key)`. Same key + same body returns the existing order (200); same key + different body → 409. Concurrent duplicates create one order.
- **Paper venue:**
  - Market orders fill at the best ask/bid with the taker fee.
  - Marketable limit orders fill as taker.
  - Resting GTC limit orders fill at their limit price with the maker fee, checked by a 1 s matcher job.
  - Non-marketable IOC orders expire.
  - A quote older than 10 s, missing, or with a null or ≤ 0 bid/ask → `REJECTED` (`STALE_PRICE`).
- **Positions and PnL:** signed contracts; weighted-average entry; realized PnL on reduce/close/flip; fees accumulated; unrealized PnL from a fresh mark price (null when no fresh mark).
- **Fill step:** fill row, order, position and audits in one transaction; retried (up to 3 attempts) on version conflicts; double fills prevented by the unique `(venue, venue_fill_id)` constraint and version checks.
- **Audit:** every transition, fill and position change writes an `audit_event` row (protobuf `EventEnvelope`) in the same transaction. Publishing to Kafka comes in slice 4.
- **Risk placeholder:** until `maryada` (slice 3), only `PAPER` orders are approved. With `TRADING_MODE=DELTA_TESTNET` every order is `RISK_REJECTED` (`NO_RISK_SERVICE`).
- **REST endpoints:**
  - `POST /api/v1/orders` (201 new / 200 duplicate) and `POST /api/v1/orders/{id}/cancel`.
  - `GET /api/v1/orders?state=`, `GET /api/v1/orders/{id}` (with transitions and fills).
  - `GET /api/v1/positions`, `GET /api/v1/pnl`.
  - Bad input → 400/404/409 with `{"error": ...}`. `limitPrice` is limited to 12 integer and 12 fraction digits, so a huge number such as `1e99999999` cannot tie up the CPU.
- **New config:** `TRADING_MODE` (`vajra.trading.mode`, default `PAPER`). The scheduler now runs 4 jobs.
- **Docs:** knowledge `0023-oms-and-paper-trading.md`; Hinglish note `08-order-lifecycle/02-paper-order-ka-safar.md`.

## DB migrations
Schema `core` (Flyway, `brahma`), `V4__oms.sql`:
- `orders` (unique `client_order_id`, `idempotency_key`, `request_hash`, optimistic `version`)
- `order_transition`
- `fill` (unique `venue, venue_fill_id`)
- `position` (PK `venue, instrument_id`, `version`)
- `audit_event` (outbox, partial index on unpublished rows)

## Contract changes
New Protobuf messages in `contracts/proto/vajra/events/v1/`: `OrderUpdated`, `FillCreated`, `PositionUpdated` (decimals as strings, wrapped in `EventEnvelope`). Additive only; `buf lint` clean. No Kafka topics yet.

## Breaking changes
None. New endpoints and tables only.

  - A paper market order returned 201 FILLED, and the same key returned 200 with the same id.
