# Phase 2 slice 3: risk gate and kill-switch

## Summary
Every order from `brahma` (core-service) now needs an approval from `maryada` (risk-service) before it can reach a venue. `maryada` uses fixed rules with no ML or LLM, fails closed, records every decision, and owns a kill-switch that halts trading, cancels open orders and flattens positions. This is the third slice of Phase 2, an enhancement, so the bump is minor.

## Changes
- **maryada approval API:** `POST /api/v1/approvals`. The first rule that fails rejects the order. Rules in order:
  1. `INVALID_REQUEST`: bad input, size < 1, or position arithmetic overflow.
  2. `VENUE_NOT_ALLOWED`: venue is not `PAPER` or `DELTA_TESTNET`.
  3. Flatten exemption: `KILL_SWITCH` + reduce-only orders are approved, even while halted.
  4. `HALTED`: kill-switch is on.
  5. `ORDER_SIZE_LIMIT`: more than 1 contract.
  6. `POSITION_LIMIT`: absolute position above 5. Orders that reduce the position are always allowed.
  7. `ORDER_RATE_LIMIT`: more than 10 approved orders in 60 s.

  An unexpected error inside the rules gives `INTERNAL_ERROR` (reject). Approvals are serialised with a Postgres advisory lock. Every decision is stored in `risk.risk_decision`.
- **Kill-switch (maryada):**
  - `POST /api/v1/kill-switch` saves the halt first ("kill always wins"). It then calls brahma `/internal/v1/kill`, which cancels open orders and flattens positions with reduce-only orders.
  - `POST /api/v1/kill-switch/resume` uses compare-and-set. If kill is pressed during a resume, the answer is 409 and trading stays halted. If brahma is unreachable, the answer is 503 and trading stays halted.
  - `GET /api/v1/kill-switch` shows the state and recent events.
  - "Last action wins": a kill that a later resume has superseded does not flatten.
- **brahma risk gate:**
  - `MaryadaRiskGate` calls maryada with a 500 ms timeout. Unreachable, timeout, bad answer → `RISK_REJECTED` (`RISK_CHECK_FAILED`).
  - A local halt flag (`core.trading_state`) rejects orders with `HALTED` even when maryada is down.
  - Orders store `riskDecisionId`.
  - The `PaperOnlyRiskGate` placeholder is removed.
- **Reduce-only re-check at fill:** if a reduce-only order would no longer reduce the position, it is cancelled instead of filled.
- **Auth:**
  - Bearer tokens from env: `RISK_API_TOKEN` (calls to maryada) and `CORE_INTERNAL_TOKEN` (maryada → brahma `/internal/**`). They are compared in constant time.
  - Deny-by-default on the servlet path; only `/actuator/health` is open. This also closes the `/api;x=y` and `%61pi` bypass paths.
  - Both services refuse to start without their tokens.
- **Compose:** brahma gets `RISK_BASE_URL`, `RISK_API_TOKEN` and `CORE_INTERNAL_TOKEN`. maryada gets `RISK_API_TOKEN`, `CORE_INTERNAL_TOKEN` and `CORE_BASE_URL`. `.env.example` has placeholders.

## DB migrations
- Schema `risk` (`maryada`), `V2__risk.sql`:
  - `risk_limit`, seeded with 1 / 5 / 10.
  - `risk_decision`.
  - `kill_switch`, single row.
  - `kill_switch_event`.
- Schema `core` (`brahma`), `V5__trading_state.sql`:
  - `trading_state`, single row.
  - Column `orders.risk_decision_id`.

## Contract changes
- New REST APIs on maryada (approvals, kill-switch) and on brahma (`/internal/v1/kill`, `/internal/v1/resume`).
- No Protobuf changes.

## Breaking changes
- **Required env vars:** both brahma and maryada now need `RISK_API_TOKEN` and `CORE_INTERNAL_TOKEN`, or they will not start. Add real values to the VPS `.env` before deploying.
- **maryada must be running:** without it, every brahma order is rejected with `RISK_CHECK_FAILED`.

## Known follow-ups
All are listed in knowledge doc 0024.
- **Must fix before slice 5 (real testnet orders):**
  - An in-flight order approved just before the halt can fill after kill, and kill then wrongly reports `flattened=true`.
  - Kill's final check should also count NEW, APPROVED, SENT and UNKNOWN orders.
  - Kill cannot flatten a position on a disabled instrument or on another venue.
  - The reduce-only cancel is local only and is not sent to the venue.
- **Hardening:**
  - Add a separate operator token for kill-switch when `dvara` is wired in.
  - A late APPROVED row, arriving after brahma's 500 ms timeout, still uses up the rate window.
  - Halt and resume are not written to brahma's `audit_event`.
