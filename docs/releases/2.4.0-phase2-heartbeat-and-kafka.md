# Phase 2 slice 4: heartbeat strategy and Kafka signal path

## Summary
The bot now trades on its own. Every 15 minutes `signal-service` sends a heartbeat signal for 1 BTCUSD contract, alternating BUY and SELL. The signal goes over Kafka to `core-service`, which places a paper order through the risk gate. `core-service` also publishes its audit outbox to Kafka. This is the fourth slice of Phase 2 and an enhancement, so the bump is minor.

## Changes
- **Contracts:** new `vajra.events.v1.SignalGenerated` with these fields:
  - `signal_id`, `strategy`, `symbol`, `side`, `order_type`, `size`, `generated_at`.

  It is always sent inside `EventEnvelope`.
- **Topics:** a one-shot compose service `kafka-init` creates the topics with `infra/kafka/create-topics.sh`:
  - topics: `signal.generated`, `order.updated`, `fill.created`, `position.updated`
  - settings: 1 partition, retention 7 days
  - auto-create stays off
  - re-running it is safe, and no service depends on it
- **signal-service heartbeat:**
  - Defaults: every `HEARTBEAT_INTERVAL_SECONDS` (default 900), BTCUSD, 1 contract, MARKET, `strategy = "heartbeat"`.
  - Each signal is stored in `signal.signal_log` first and then published, keyed by symbol.
  - Unpublished rows are retried on the next tick.
  - BUY/SELL alternation continues after a restart.
  - The Kafka producer connects lazily, so the service starts even when Kafka is down.
  - Startup fails unless `TRADING_MODE` is `PAPER` or `DELTA_TESTNET`.
- **core-service signal consumer:**
  - Consumer group `core-service`, 1 thread, manual ack after the order row is written.
  - Idempotency key is `signal-<signal_id>`, so a duplicate signal gives exactly one order.
  - Invalid messages (bad bytes, wrong payload, unknown symbol, size < 1) are logged at ERROR and skipped.
  - Transient errors are retried 5 × 2 s.
  - Signals go through the same local halt check and risk gate as manual orders.
  - An order stuck after a failure is logged at ERROR.
- **core-service outbox publisher:**
  - Every 1 s, unpublished `core.audit_event` rows are sent to the topic named by their event type, keyed by symbol, with `acks=all`.
  - A row is marked published only after the broker acknowledges it.
  - If Kafka is down, rows wait and orders keep working. Kafka is not part of the health check.
- **Orders:** `orders.signal_id` is stored and returned in `GET /api/v1/orders/{id}` as `signalId`.
- **Idempotency fix:** a transient optimistic-lock conflict is now marked as retryable. It is still a 409 over REST. The manual order hash is unchanged.
- **Config:**
  - `KAFKA_BOOTSTRAP` for core-service and signal-service.
  - `HEARTBEAT_INTERVAL_SECONDS` and `TRADING_MODE` for signal-service.
  - `SIGNALS_ENABLED` for core-service (default true).
  - core-service scheduler jobs go from 4 to 5.
- **Docs:**
  - knowledge doc `0026-heartbeat-and-kafka-signal-path.md`
  - Hinglish note `07-kafka-and-events/03-heartbeat-signal-ka-safar.md`

## DB migrations
- Schema `core` (Flyway, core-service), `V6__signals_and_outbox_key.sql`:
  - `orders.signal_id` plus a partial unique index
  - `audit_event.event_key`
- Schema `signal` (Alembic, signal-service), `0002_signal_log`:
  - table `signal_log`, with `size >= 1` and an index on `generated_at`

## Contract changes
- Additive only: the `SignalGenerated` proto. `buf lint` is clean and the breaking check passes.
- New Kafka topics: `signal.generated`, `order.updated`, `fill.created` and `position.updated`.
- REST: `signalId` is added to order details. This is an additive change.

## Breaking changes
- **New required config:** signal-service needs `KAFKA_BOOTSTRAP` (compose sets it).
- **First deploy:** run `scripts/compose.sh up -d --build` so `kafka-init` creates the topics.
- **Paper trading starts:** the bot now places a paper order every 15 minutes. To stop it, set `HEARTBEAT_ENABLED=false` on signal-service or `SIGNALS_ENABLED=false` on core-service.

    - A transient 409 dropped the signal.

  - Kafka was stopped for about 60 s. core-service stayed healthy and a manual order filled. After Kafka came back, the outage-time signal became exactly one order and the outbox drained.

## Known follow-ups
All of these are also in knowledge doc 0026.
- **Before Phase 4 strategies:** add a maximum signal age, so old signals are not executed after a long outage.
- **Heartbeat drift:** alternation follows the last generated signal, so rejected signals can shift the paper position. Risk's 5-contract limit bounds it.
- **Outbox:** a row that can never be sent blocks the queue with only a WARN. Escalate after N failures. The publisher is safe for a single instance only.
- **Slice 5:**
  - pass `TRADING_MODE` to core-service in compose
  - reconciliation for stuck NEW/APPROVED/SENT orders
- **Tests:** the retry path has a unit test but no integration test.

## Rollback notes
- **Quick stop without rollback:** set `HEARTBEAT_ENABLED=false` on signal-service, or `SIGNALS_ENABLED=false` on core-service.
- **Full rollback:** redeploy the 2.3.0 images and compose. The new tables and columns are unused by older code and can stay.
- **Removing the schema changes:**
  - `core`: drop `orders.signal_id` and its index and `audit_event.event_key`, then delete the `V6` row from `core.flyway_schema_history`.
  - `signal`: run `alembic downgrade 0001`.
- **Kafka:** topics can stay. Old code does not use them.
